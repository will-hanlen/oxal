instead of installing views and placing data manually,
all code and data in the tree is managed by an "app".
this is because the dataful parts of the tree are "locked"
with either a form or a lens. forms constrain a subtree's shape
so that user can manually place data in there. views are
transformers that either transform the output of a form or the
output of another view.

apps have their shape governed by a gate like
|=  [title=iota globals=data locals=data]
^-  (map pith view)

there are a list of apps.
globals are store globally under /globals
locals are stored globally under /apps/[title=iota]/local

globals are things like "who do i generally want to sync public data from"

the globals and locals are used to build the shape of the app's views.
once the views are in place, the user interacts with the app through
its forms.

i think i want to move away from html based interfaces.
i don't want users to be writing interfaces.
i don't really want them thinking about sail.
i think it will be totally possible to just have them specify %form-s and %lens-s.

then in the very distant future, maybe there's some convention which
uses some namespace convention to generate rich interfaces.

but the first round of things is just done in the static-datastar model.
no sse for now.

just get the spreadsheetedness to feel really good.

i think the problem that i'm going to run into is that statically rendering a whole
tree is really slow. so the ui actually needs some local state that it can use
to determine which parts of the tree it actually needs to render.

i guess this is an "app".
in its local state it stores info like:
- which subpath am i rendering
- which directories are unfolded
- what is the manx-ified rendering of this node.

so while i'm building out the app system, i'll just use the htmx-static renderer.

then once it works, i'll strip out the gall and eyre stuff.

then i'll build a namespace renderer within the namespace as an app.

then i'll figure out how to pipe its reactive output through eyre
so that it works as a mast-like system.
